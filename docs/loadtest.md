# 對話壓力測試

`scripts/loadtest.py` 讓好幾個「使用者」同時透過聊天 API 提問，人數一階一階往上加（預設 1、2、5、10 人），記錄每一階的回應時間、錯誤率和記憶體高峰。用來找出系統在這台機器上大約能同時服務幾個人。

**只在需要時手動執行**，不屬於一般測試：每一題都是真的對話，會用到聊天模型的額度，也會讓機器滿載一段時間。

## 執行

前提：Docker 服務都在跑，`docker/.env` 設定了管理員帳號。

```
uv run python -m scripts.loadtest                              # 1、2、5、10 人，每人 3 題
uv run python -m scripts.loadtest --steps 1,3,5 --questions 2  # 自訂人數和題數
uv run python -m scripts.loadtest --no-kb                      # 不用知識庫，只測聊天模型
```

| 參數 | 預設 | 說明 |
|---|---|---|
| `--steps` | `1,2,5,10` | 每一階同時提問的人數，由少到多，**最多 10 人** |
| `--questions` | 3 | 每個人在每一階依序問幾題（每題開一個新對話） |
| `--pause` | 10 | 每一階之間休息幾秒 |
| `--stop-error-rate` | 0.2 | 某一階的錯誤率超過 20% 就不再加人 |
| `--no-kb` | 關 | 不建立知識庫。預設會用 `test_data/rag` 的 25 份 md 建一個暫時的知識庫，讓每次提問都經過檢索 |
| `--out` | `data/` | 報告目錄（`data/` 不納入 git） |

流程：

1. 用 `docker/.env` 的管理員帳號登入（密碼不會印出）。
2. 建立暫時的知識庫並上傳測試文件，等它們處理完（`--no-kb` 時跳過）。
3. 每一階同時開 N 個「使用者」，每人依序問幾題。題目取自內建題庫的一般問答。
4. 每一階結束後，從監控資料讀出這段期間各容器的記憶體高峰。
5. 寫出報告 `data/loadtest-<時間>.md` 和 `.json`，刪除暫時的知識庫和對話。

預設會發出 (1+2+5+10)×3 = **54 次對話**。所有使用者都是同一個管理員帳號，但每題都是不同的對話，所以不會被「這個對話正在產生回覆」擋下。

## 報告裡的數字

| 數字 | 意思 |
|---|---|
| 開始回應 | 從送出問題到收到第一筆串流資料的時間，包含檢索和等待模型開始回答 |
| 回答完成 | 從送出問題到回答全部傳完的時間 |
| p50／p95 | 一半的請求在 p50 以內完成；95% 的請求在 p95 以內完成。看上限時以 p95 為準 |
| 錯誤率 | 失敗的請求比例，錯誤原因列在報告最後 |
| 每分鐘完成 | 這一階每分鐘完成幾個回答 |

## 怎麼判斷上限

先訂一個可以接受的標準，例如「95% 的回答在 30 秒內開始」。人數往上加時，第一個超過標準或開始出錯的那一階，就是目前的上限。

看結果時注意：

- **聊天模型的限制通常最先碰到**。Gemini 有每分鐘的請求上限（依方案不同），超過會回 503「Gemini 配額已用完或請求太頻繁」。這是額度限制，不是系統本身的上限。用 Ollama 時，瓶頸則是主機的 GPU 或 CPU。
- **embedder 一次只算一個請求**（其他並行數見 [services.md](services.md#並行數與批次大小)）。很多人同時問時，「問題轉向量」會排隊，「開始回應」的時間會跟著拉長。
- 數字只代表**測試當下這台機器、這個模型**的情況。換模型、換硬體，或同時開著其他程式（例如 RAGFlow），都要重測。
