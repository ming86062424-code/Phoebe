# RAG 評測

`evals/test_rag_quality.py` 用固定的題庫實際問一次知識庫，分開評兩件事：

- **檢索**：該找到的段落有沒有排進前幾名。
- **回答**：模型有沒有根據找到的資料正確回答、有沒有自己編造。

兩件事分開評，出問題時才知道要改哪一邊：檢索沒命中就調切段、權重或 embedding；檢索命中但回答錯，就調提示詞或聊天模型。

**只在需要時手動執行**，不屬於一般測試。它會呼叫聊天模型和裁判模型，用 Gemini 時都會計費。

## 執行

前提：

- Docker 服務都在跑。
- `docker/.env` 設定了管理員帳號和 `GEMINI_API_KEY`。
- `test_data/rag/` 有 25 份 md 測試文件。

```
uv run --group eval pytest evals/test_rag_quality.py
```

流程：

1. 用 `docker/.env` 的管理員帳號登入 `http://localhost:8000`。
2. 建立一個暫時的知識庫，上傳 25 份 md，等它們處理完成。
3. 每一題都開一個新的對話，透過聊天 API 實際提問。
   - 用的是使用者實際會用到的檢索、提示詞與聊天模型。
   - 聊天模型是系統設定頁目前選的那個。
4. 評分，寫出報告。
5. 刪除暫時的知識庫和對話。

用的是一般的 pytest。沒有用 DeepEval 的 `deepeval test run`，原因有兩個：

- 要把每個指標的分數和理由寫進自己的報告。
- `deepeval test run` 在 Windows 上讀不回它自己的結果，會出現 portalocker 的警告。

### Gemini 免費方案的限制

Gemini API 免費方案**每個模型每分鐘最多 15 次請求、每天 500 次**，額度依模型分開計算。一次完整評測大約要：

- 聊天模型：54 次對話。
- 裁判模型：約 390 次。要評回答的 44 題，每題 2–3 個指標，每個指標呼叫裁判 2–4 次（拆句、逐條判斷、寫理由）。

所以聊天和裁判要用**不同的模型**，各用各的額度。預設聊天是 `gemini-3.5-flash-lite`、裁判是 `gemini-3.1-flash-lite`。如果兩者設成同一個，一次評測就會超過每日上限。

聊天模型的每日額度是評測和平常聊天共用的。當天如果也有在聊天，一次評測（50 多次對話）加上平常使用，可能讓聊天模型的額度用完，評到一半出現「Gemini 免費方案今日的請求次數已用完」。

- 被限流時（Gemini 的 429，或系統回覆「Gemini 配額已用完或請求太頻繁」），評測會照 Gemini 建議的秒數等待後重試，最多 6 次。指標也是一個一個依序呼叫，不會同時發出。
- **跑完要 1 小時左右**，大部分時間在等每分鐘的額度恢復。
- 碰到每日上限時評測不會等待重試：還沒評的題目會直接記成「Gemini 免費方案今日的請求次數已用完」。可以隔天再跑，或用 `EVAL_JUDGE_MODEL` 暫時換另一個額度還有剩的模型。
- 只想重跑部分題目，用 pytest 的 `-k` 篩選。`-k` 是用子字串比對測試名稱，而每題都有 `test_retrieval` 和 `test_answer` 兩個測試，所以：
  - 只重測關鍵字和語意題的檢索（不用裁判模型）：`-k "test_retrieval and (keyword or semantic)"`。這會連 `keyword-question-*`、`semantic-phrase-*` 一起選到。
  - 要連回答一起評，再拿掉 `test_retrieval and`；這樣會呼叫裁判模型、消耗額度。

報告寫到 `evals/reports/rag-<時間>.md`（給人看）和 `.json`（完整的分數與裁判理由）。這個目錄不納入 git。

## 題庫

題庫在 `evals/rag.dataset.json`，共 54 題，取自 `test_data/rag/README.md`，不足的部分另外補題：

| 類別 | 題數 | 用途 | 評什麼 |
|---|---|---|---|
| 一般問答 | 25 | 每份文件一題 | 檢索＋回答 |
| 關鍵字（只輸入代號） | 5 | 只輸入專有代號，例如 `FL-360C`，測關鍵字那一路 | 只評檢索 |
| 關鍵字（完整問題） | 5 | 同樣的代號放進完整問題，例如「FL-360C 濾網多久要更換？」 | 檢索＋回答 |
| 語意（簡短詞組） | 5 | 不用文件字詞的短詞組，例如「房間潮濕衣服晾不乾」，測向量那一路 | 只評檢索 |
| 語意（完整問題） | 6 | 同樣的意思寫成完整問題，例如「家裡很潮濕，衣服晾不乾怎麼辦？」；另有 1 題只描述情境：「官網打不開了，值班工程師要在多久內回應？」（文件用的詞是「P1」） | 檢索＋回答 |
| 容易混淆 | 5 | 不同文件有相似的段落或代碼，看會不會抓錯，例如「除濕機面板顯示 P1 是什麼意思？」容易抓成值班的「P1 緊急」告警 | 檢索＋回答 |
| 知識庫沒有答案 | 3 | 應該回答「知識庫中沒有相關資訊」，不能編造 | 只評回答 |

關鍵字和語意各有兩種寫法，對應同樣的來源：比較兩者的檢索結果，就能看出關鍵詞單獨出現時，和與其他字詞連成完整句子後，排名有什麼差別。關鍵字和語意兩類中，只輸入代號或短詞組的題目不是完整的問題，所以不評回答，也沒有標準答案。這條規則只適用於這兩類：「容易混淆」裡的「錯誤代碼 E2」雖然也只是代碼，仍然評回答，因為要看回答有沒有講對是哪台機器的錯誤碼。除了「知識庫沒有答案」，其他要評回答的題目都有標準答案。

每題都標了「應出現的來源」，也就是檔案加上 `##` 段落標題。原本 README 裡「容易混淆」的問題附有括號說明，例如「（只問 DL-9）」，題庫已改寫成完整的問題，例如「DL-9 智慧門鎖保固幾年？」。原本的「10 分鐘內要做什麼？」看不出問的是什麼，改寫成「官網打不開了，值班工程師要在多久內回應？」後，查的段落和答案都跟一般問答的「P1 告警要在多久內回應？」相同，已不算容易混淆，所以移到語意（完整問題）；容易混淆改用「除濕機面板顯示 P1 是什麼意思？」。

題庫要固定，前後的分數才能比較。**題庫從 54 題這一版（2026-10-30）開始固定**，之後的評測都跟它比；在這之前的報告（43 題、53 題）題目不同，不能拿來比較。想測別的內容，請另外建一份題庫，不要改原本這份。

## 評什麼

### 檢索（不需要裁判模型）

直接比對聊天時實際檢索到的段落，看「應出現的來源」排在第幾名。

| 數字 | 意思 |
|---|---|
| 前 N 名命中 | 應出現的來源有沒有出現在檢索結果裡（N 是 `KB_TOP_K`，預設 5） |
| 第 1 名命中 | 是否排在第一名 |
| MRR | 排名倒數的平均：第 1 名算 1、第 2 名算 0.5，沒找到算 0。越接近 1 越好 |

這部分由程式判斷，結果穩定、沒有成本。「知識庫沒有答案」的題目沒有應出現的來源，所以不評檢索。

### 回答（裁判模型評分，0–1 分，0.7 分以上算通過）

| 指標 | 看什麼 | 用在哪些題目 |
|---|---|---|
| Faithfulness | 回答的內容是否都能在檢索到的段落裡找到根據，有沒有自己編造 | 要評回答的 44 題 |
| Answer Relevancy | 有沒有回答到問題 | 有標準答案的 41 題 |
| 答案正確（GEval） | 是否包含標準答案的關鍵事實，例如數字、名稱、條件，而且沒有矛盾 | 有標準答案的 41 題 |
| 承認沒有答案（GEval） | 是否明確說知識庫沒有相關資訊，而且沒有編造細節 | 「沒有答案」的 3 題 |

沒有用 DeepEval 的 Contextual Relevancy／Precision／Recall：

- 每題只有一段是答案。前 5 段裡另外 4 段本來就不相關，Contextual Relevancy 會一直偏低，看不出好壞。
- 「有沒有找到、排第幾」已經由上面的程式判斷，不需要再花裁判模型的成本。

### 裁判模型

由 `EVAL_JUDGE_MODEL` 決定，預設 `gemini-3.1-flash-lite`（刻意和預設的聊天模型 `gemini-3.5-flash-lite` 不同，額度才不會互搶）：

- `gemini-` 開頭的名稱用 Gemini，需要 `GEMINI_API_KEY`。
- 其他名稱用本機 Ollama 的模型。

這個設定只有手動跑評測時會讀，容器不使用。它可以放在環境變數、專案根目錄的 `.env` 或 `docker/.env`。

Ollama 上的小模型（例如 `qwen3.5:4b`）判斷中文「是否有根據」不太可靠，所以預設用 Gemini。

## 怎麼看結果

- **先看檢索**：檢索沒命中的題目會列在報告裡，附上實際找到的前幾段。
  - 關鍵字題沒命中，代表關鍵字那一路有問題，例如斷詞。
  - 語意題沒命中，代表向量那一路有問題。
  - 同一個來源，只輸入代號（或短詞組）命中、寫成完整問題卻沒命中，代表句子裡其他字詞稀釋了關鍵詞；反過來則代表單獨的詞缺少上下文。
- **再看回答**：沒通過的題目會列出回答、標準答案和裁判的理由。
  - **Faithfulness 低**：可能是模型加了知識庫以外的內容。提示詞允許「資料不足時補充一般知識並註明」，所以補充的部分也會被扣分。要看理由判斷是真的編造，還是有註明的補充。
  - **答案正確低，但檢索有命中**：問題在回答這一段，例如提示詞或聊天模型。
- **分數僅供參考**：裁判模型也會出錯，同一份回答每次的分數可能差一點。要比較改動前後，請在相同條件下跑，也就是相同的題庫、聊天模型和裁判模型，並以多題的平均來看。

## 限制

- 題庫都是 md，只測文字。PDF 的解析品質（LiteParse、LightOnOCR）要另外準備有標準答案的 PDF 題目。
- 只測單輪問答。系統每則訊息本來就各自檢索（不改寫追問），所以單輪評測就能反映實際的檢索。追問的情境等之後做 Agent 時再評。
- Faithfulness 只看文字。如果知識庫有頁面圖，而模型是從圖片讀到答案的，可能會被誤判成編造。目前的題庫都是 md，沒有圖片，所以不受影響。
