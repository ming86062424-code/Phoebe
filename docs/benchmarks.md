# 效能測試

`scripts/benchmark.py` 用一組固定的情境實際跑一次系統，產生一份報告，記錄每個任務各階段的時間和記憶體、顯存高峰，並和基準比較。用來判斷某次改動（換設定、換硬體、改解析流程）讓系統變快還是變慢。

**只在需要時手動執行**。它要跑好幾分鐘、會讓機器滿載，數字也會受背景程式影響，所以不屬於平常的自動化測試，平常開發時不會執行。

## 執行

前提：Docker 服務都在跑（包括 `monitor`），`docker/.env` 有設定管理員帳號，`test_data/` 裡有情境用到的檔案。

```
uv run python -m scripts.benchmark                     # 全部任務，每項 3 次
uv run python -m scripts.benchmark --skip-chat         # 不測 AI 對話（雲端模型會計費）
uv run python -m scripts.benchmark --parsers liteparse text --runs 2
uv run python -m scripts.benchmark --set-baseline      # 這次的結果設為新的基準
```

| 選項 | 說明 |
|---|---|
| `--runs` | 每個任務跑幾次，預設 3。第一次算「冷啟動」 |
| `--parsers` | 只測這些解析器（`liteparse`、`lightonocr`、`text`）。目前不可用的解析器會自動略過，例如沒開 vLLM 時的 LightOnOCR |
| `--skip-chat` | 不測 AI 對話 |
| `--set-baseline` | 把這次的結果複製成 `docs/benchmarks/baseline.json` |
| `--compare` | 指定要比較的基準檔，預設 `docs/benchmarks/baseline.json` |
| `--threshold` | 比基準差多少算警告，預設 0.25（25%） |
| `--scenario`、`--out` | 情境檔、報告目錄 |

腳本會用 `docker/.env` 的管理員帳號登入，因為讀取監控資料需要管理員權限。測試用的知識庫和對話，跑完會全部刪除。

## 測什麼

情境在 `scripts/benchmark_scenario.json`：

| 任務 | 內容 |
|---|---|
| 文件處理 | 草莓園 PDF（12 頁）分別用 LiteParse、LightOnOCR 處理；一份 md 用文字解析處理 |
| 搜尋測試 | 對草莓園的知識庫問 2 個固定的問題 |
| AI 對話 | 同樣 2 個問題，實際呼叫聊天模型 |

情境要固定才能比較。想測別的內容，請另存一份情境檔，用 `--scenario` 指定，不要改原本那份。測試檔案放在 `test_data/`，不在 git 裡，換電腦時要另外複製。

## 數字從哪裡來

腳本**不自己計時**，而是重用系統本來就在記錄的監控資料（[monitoring.md](monitoring.md)）：

- **各階段時間**：每個任務結束後，從監控的事件紀錄讀出這次的總時間和各階段時間，例如解析、向量、寫入、第一個回應。
- **記憶體與顯存高峰**：讀取 monitor 服務在這個任務期間的取樣，算出每個容器、GPU，以及全部容器加總的最高值。
  - monitor 每 5 秒取樣一次，所以腳本會等到任務結束後的下一次取樣才讀，避免很短的任務（例如 0.2 秒的搜尋）沒有任何取樣。
  - 比 5 秒還短的瞬間高峰可能量不到，看的是任務期間的大致高峰。

## 報告

輸出到 `docs/benchmarks/`，檔名是執行時間，例如 `20261027-1430.md`（給人看）和 `.json`（給比較用）。

- **環境**：git commit（有未 commit 的修改會標出）、模式（LightOnOCR 模式或 GPU embedding 模式）、聊天模型、GPU、Docker 虛擬機記憶體、其他專案的容器佔多少記憶體，以及會影響數字的設定（`INGEST_CONCURRENCY`、`OCR_CONCURRENCY`、KV cache 大小等）。
- **結果**：每個任務分「冷啟動」和「平均」兩欄。
  - 冷啟動是第一次執行，包含模型載入、快取建立，通常比較慢。
  - 平均是之後幾次的平均，**比較時看這一欄**。
  - 列出總時間、各階段時間，以及 embedder、ingest、web、milvus、vllm、GPU、全部容器的記憶體高峰。
- **與基準比較**：平均值比基準差超過 25% 的項目會列為警告（⚠）。
  - 很小的差異不算，例如時間差不到 0.5 秒、記憶體差不到 256 MB，避免零點幾秒的抖動也被當成變慢。
  - 環境和基準不同時（例如基準在 CPU 模式、這次在 GPU 模式），會先列出差異，提醒比較僅供參考。

報告要不要 commit 由你決定：值得留下的結果（例如新的基準、換硬體前後）可以 commit，當作歷史紀錄。

## 怎麼比較才有意義

- **條件要一樣**：同一份情境、同一種模式。也要留意背景負載，例如 RAGFlow 開著就會多佔 3–5 GB 記憶體；腳本偵測到其他專案的容器佔超過 1 GB 時會提醒。
- **先有基準**：第一次跑完，用 `--set-baseline` 設為基準。之後每次重要的改動後再跑一次；確定新的結果比較好，再把它設為新的基準。
- **看階段，不只看總時間**：總時間變慢時，看是解析、向量還是 LLM 的第一個回應變慢。
- **警告不是失敗**：數字會因背景負載而波動，警告是提醒你去看看，不代表一定有問題。等累積幾次結果、知道正常的波動範圍後，再調整 `--threshold`。目前也還沒訂「多快才合理」的絕對目標，等有實際使用經驗後再訂。
