# 監控頁面

管理員登入後，側邊欄有「監控」，可以確認每個任務花了多少時間，以及各時間點的記憶體、CPU、GPU 用量。這份文件說明頁面上的資料從哪裡來、怎麼看，以及設計上的取捨。

## 三個分頁

| 分頁 | 內容 | 更新 |
|---|---|---|
| **事件紀錄** | 每個任務一列：開始時間、類型、狀態、名稱、總時間、各階段耗時、詳細資訊。可以依類型篩選，往下可以載入更早的紀錄 | 每 10 秒 |
| **資源使用** | 上面是「目前用量」：每個容器的記憶體、佔上限的比例、CPU，全部容器的總量和 GPU；下面是「詳細取樣紀錄」，可以選時間和來源，列出每一次的取樣 | 每 10 秒 |
| **圖表** | 選一段時間（15 分鐘到 48 小時），上方的「任務」列把每個任務畫成一段橫條，下方依序是各容器的記憶體、全部容器的記憶體總量、各容器的 CPU、GPU 顯存、GPU 使用率。滑鼠移到圖上，所有圖表會在同一個時間點顯示數值，方便對照「這個高峰是哪個任務造成的」 | 每 15 秒 |

## 記錄哪些任務

| 類型 | 什麼時候記錄 | 各階段 | 詳細資訊 |
|---|---|---|---|
| **文件處理** | ingest 處理完一份文件（成功或失敗） | 解析、向量（embedding）、寫入（Milvus） | 解析器、頁數、chunk 數、錯誤訊息 |
| **AI 對話** | 一次回答結束（完成、失敗或中途中斷） | 向量（問題）、檢索、載入附圖、第一個回應、思考、回答 | 使用者、供應商與模型、知識庫、參考資料數、附圖數、是否為重新產生、錯誤訊息 |
| **搜尋測試** | 知識庫頁的搜尋測試 | 向量（問題）、檢索 | 使用者、知識庫、結果數、向量權重 |

AI 對話各階段的意思：

- **第一個回應**：從呼叫模型到收到第一段回應。如果模型會先思考，第一段回應就是思考內容。
- **思考**：從第一段回應到開始出現答案文字。只有模型先思考時才有這一項（`CHAT_THINK=true`）。
- **回答**：從答案的第一個字到結束。

使用者感受到的「等很久才有字」，看的是「第一個回應」加上「思考」。

狀態：完成、失敗、中斷（對話中途關掉頁面或網路斷線）、暫停（ingest 停止時文件留待下次處理）、已刪除（處理中的文件被刪掉）。

**不記錄對話內容**，只記錄時間、模型和數量。事件的名稱是對話標題或檔名。LLM 更詳細的紀錄（token 數、prompt 等）之後改用 Langfuse。

記錄失敗（例如資料庫被鎖住）只會寫到 log，**不會影響任務本身**。

## 資源用量從哪裡來

Docker 裡的 `monitor` 服務每 5 秒取樣一次（`MONITOR_INTERVAL_SECONDS`）：

- **所有容器**：透過 Docker 的 API 讀取每個容器的記憶體和 CPU，**包括其他專案的容器**（例如 RAGFlow），因為大家共用同一台 Docker 虛擬機的記憶體。
  - 記憶體的算法和 `docker stats` 一樣，扣掉可以隨時釋放的檔案快取。
  - CPU 用前後兩次取樣的差值計算，100% 等於一個核心。所以每個容器的第一次取樣沒有 CPU 數值。
- **GPU**：執行 `nvidia-smi`，讀取顯存用量、總量和使用率。顯存是整張卡的用量，包含 Windows 桌面等 Docker 以外的程式。

圖表上：

- Phoebe 的每個服務各有固定的顏色，例如 embedder 一定是同一個顏色。其他專案的容器合併成一條灰色的「其他容器」。
- 選的時間越長，每個點代表的時間區間越長，每條線最多約 360 個點，**同一區間取最大值**，所以短暫的高峰不會被平均掉。
- monitor 有一段時間沒在取樣時，線會斷開，不會連成一條假的直線。

## 資料存在哪裡

- 另一個 SQLite 檔 `monitor.db`，和 `app.db` 放在同一個地方（Docker 裡是 `phoebe_phoebe-db` volume）。
  - 分開存放的原因：取樣每幾秒寫一次，不和帳號、對話的資料庫搶寫入；不需要時可以整個刪掉，不影響其他資料。
- 保留期限：
  - 資源取樣保留 48 小時（`MONITOR_RESOURCE_RETENTION_HOURS`），約 30–60 MB。
  - 任務事件保留 30 天（`MONITOR_EVENT_RETENTION_DAYS`）。
  - 由 monitor 服務每 10 分鐘清除一次過期資料。
- 想清空所有監控資料：停掉服務後，刪掉 volume 裡的 `monitor.db`、`monitor.db-wal`、`monitor.db-shm`，下次啟動會自動重建。

## 對系統的負擔

- **任務計時**：只是在每個階段前後讀時鐘，結束時寫一筆資料到 SQLite，相對於動輒幾秒的任務可以忽略。
- **monitor 服務**：每 5 秒呼叫一次 Docker API、執行一次 `nvidia-smi`，寫十幾列資料。它沿用 web 的映像，常駐記憶體約幾十 MB。
- **沒有加 Prometheus、Grafana 這類常駐的監控系統**：它們加起來要幾百 MB 到 1 GB 以上的記憶體，對這台本來就吃緊的 Docker 虛擬機不划算。等系統要長期上線、多人使用時再考慮。

## 安全：Docker socket

monitor 需要掛載 `/var/run/docker.sock` 才能讀取所有容器的用量。

- **這個 socket 等同 Docker 的完整控制權**：能讀取它的程式，理論上也能建立、刪除容器。雖然以唯讀方式掛載，但唯讀只限制檔案本身，不限制透過它呼叫的 API。
- 降低風險的做法：
  - monitor 只呼叫讀取用的 API（容器列表、用量）。
  - 不對外開任何 port。
  - 不載入 `docker/.env`，拿不到 `GEMINI_API_KEY` 等密鑰。
  - 以 web 映像的一般使用者（UID 1000）執行，只額外加入 socket 所屬的群組。
- 不想承擔這個風險時，可以不啟動 monitor：`docker compose stop monitor`。事件紀錄照常運作，只是資源分頁和圖表沒有資料。

## 部署與設定

monitor 是 `docker compose up -d` 預設會啟動的服務。

- **沒有 NVIDIA GPU 的機器**：monitor 會因為找不到 GPU 而無法啟動。把 `docker/docker-compose.yml` 裡 monitor 的 `deploy` 那段註解掉即可，只是少了 GPU 資料。
- **在 Linux 上**：docker.sock 通常屬於 `docker` 群組，而不是 Docker Desktop 上的 root 群組。把 monitor 的 `group_add: ["0"]` 改成 `docker` 群組的 GID（`getent group docker` 可以查到）。
- **本機開發模式**（在主機上直接跑 uvicorn）：事件照樣會記錄到 `data/monitor.db`；資源用量要有 Docker 的 monitor 服務才有，頁面會顯示「monitor 服務沒有在取樣」。
- 設定（`docker/.env`）：

  | 設定 | 預設 | 說明 |
  |---|---|---|
  | `MONITOR_INTERVAL_SECONDS` | 5 | 多久取樣一次 |
  | `MONITOR_RESOURCE_RETENTION_HOURS` | 48 | 資源取樣保留幾小時 |
  | `MONITOR_EVENT_RETENTION_DAYS` | 30 | 任務事件保留幾天 |

## 和 `scripts/monitor_resources.py` 的差別

那支腳本是在主機上手動執行、把一次測試的用量記到 CSV，適合做基準測試，見 [parser-benchmarks.md](parser-benchmarks.md#怎麼記錄硬體用量)。監控頁面則是系統一直在記錄，隨時打開就能看。兩者讀的是同樣的數據來源（`docker stats` 的算法和 `nvidia-smi`）。
